# Server integrations

The Express server exposes public, read-only `GET /api/music`, `GET /api/activity`, and `GET /api/clips?platform=youtube|twitch` routes. They do not require Manus authentication, a session, or a database. There is no credential-input or OAuth callback endpoint. The shared TypeScript contracts live in `shared/integrations.ts`. Missing credentials return HTTP 200 with `status: "disconnected"` and empty data, never sample results disguised as live data. Provider failures return HTTP 200 with `status: "error"` and a safe message; an invalid clips platform returns HTTP 400. The frontend must use the returned `rankingLabel`, not promise an exhaustive all-time ranking.

## Environment and private setup

Set these names only in the server's secure deployment environment or secret manager: `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET`, `SPOTIFY_REFRESH_TOKEN`, `TWITCH_CLIENT_ID`, `TWITCH_CLIENT_SECRET`, and `YOUTUBE_API_KEY`. Never use a `VITE_` prefix, expose them through public runtime configuration, put them in browser code, paste them in chat, commit them, or store them in client storage. No credentials were provided or written during implementation. Configure only the providers you want, then restart the Express process. A static-only frontend deployment cannot serve these endpoints.

For Spotify, register your own app in the Spotify Developer Dashboard. In your own secure local/server setup, use Spotify's Authorization Code flow with a registered redirect URI and unpredictable, verified `state`. Authorize the intended account with `user-library-read`, `playlist-read-private`, and `user-read-playback-state`. `playlist-read-private` lets the server inspect visibility, not publish private playlists. The server deliberately excludes followed and collaborative playlists that the account does not own, so `playlist-read-collaborative` is unnecessary. Neither `user-read-email`, write scopes, nor `user-read-currently-playing` is needed: playback comes from `/me/player`, whose scope is `user-read-playback-state`. Exchange the one-time authorization code on your trusted server using the app's client ID and secret; put the resulting refresh token directly into your secret manager. Consult Spotify's official flow instructions rather than a public token-generator site. The integration exchanges the refresh token with Basic authentication at the token endpoint, stores access tokens only in process memory, refreshes before expiry, and retains a rotated refresh token in memory when returned. If a rotated refresh token replaces the original, the operator must securely update the secret manager for future restarts. It never prints or returns token values. Spotify currently documents a six-month refresh-token lifetime; refreshing an access token does not extend it, and expiration/revocation requires a new authorization performed by the operator outside this application. [1] [2]

## Spotify behavior and 2026 limitations

Spotify's February 2026 Development Mode changes took effect on February 11 for new apps and March 9 for existing apps. Development Mode requires the app owner to maintain Spotify Premium; new additions are limited to one client ID per developer and five users per app, with existing allocations grandfathered. Extended Quota Mode apps are not affected by these Development Mode changes. The playlist-content endpoint changed from `/playlists/{id}/tracks` to `/playlists/{id}/items`, and nested `track` fields became `item`. Content access is restricted to playlists the authorized user owns or collaborates on. Other users' playlists cannot be enumerated through the old `/users/{id}/playlists` endpoint, and popularity fields were removed. This integration uses `/me`, `/me/tracks`, `/me/playlists`, `/playlists/{id}/items`, and `/me/player`, not removed bulk-track or artist-top-track endpoints. Normalization accepts both `item` and legacy `track` wrappers, and `items.total` or legacy `tracks.total`. [5] [6] [7]

The live music snapshot samples up to 100 saved tracks, the first 100 account playlists, and up to six **owned, explicitly public** playlists. Each selected public playlist contributes at most 100 items. Pagination uses at most two pages of 50 for each collection. The response includes up to 24 unique album covers derived from saved tracks and the selected public-playlist tracks, plus real playlist metadata and provider totals. These are library samples, not a claim about favorite albums, frequency, popularity, or the full library. Removed/local/null/episode tracks are omitted from album normalization. Missing playlist totals are `null`, not guessed. Saved-track album artwork is intentionally public as requested; there is no saved-track listing or full playlist track list in the response. [6] [7]

Privacy is fail-closed: only `public === true` and a matching current-user owner ID pass the gate; `false`, `null`, omitted visibility, and other ownership are excluded before playlist-content requests. Visibility is rechecked against playlist details after reading items, before any playlist metadata or its album art is published. A failed recheck drops that playlist and its album art. A track independently present in saved tracks may still contribute artwork, as explicitly requested. Private Spotify playback sessions are suppressed, along with local/unsupported playback items. Do not put private information in a public playlist name or description. Normal cache freshness still applies: if a formerly public playlist is changed to private, a snapshot already cached as public may remain for up to approximately 80 seconds; restart the process to immediately clear memory caches. This is not an instantaneous privacy-change monitor.

`MusicResponse.nowPlaying` has `artists: string[]`, `progressMs`, `durationMs`, and `isPlaying`; values describe the cached snapshot and do not control playback. `playbackStatus` distinguishes `playing`, `paused`, `inactive`, `disconnected`, and `error`. HTTP 204, no current track, or a private session yields `inactive` and `nowPlaying: null`. Playback failures do not erase a successfully loaded library, and a library failure can still return a successful playback snapshot. `status: "error"` signals any failed component; `message` explains partial availability safely. [8]

## Clips and embedding

Twitch performs a users lookup and then queries broadcaster clips without a date filter. Twitch documents that this means all available dates and descending views. The server samples at most two pages of 50, re-sorts supplied `view_count` values, and returns up to 12 clips. Its label describes **top available Twitch clips by views, all available dates, at most 100 sampled**—not a complete historical archive or a fabricated rolling-window leaderboard. Missing views remain `null`, sorted after known values. No live status is inferred from clip availability; this integration does not add `/api/stream`. [4]

YouTube queries `search.list` with the exact channel ID, `type=video`, `order=viewCount`, and `videoEmbeddable=true`, at most two pages of 50. It then uses `videos.list` to retrieve statistics, duration, current channel ownership, public visibility, and embedding status. Only public, processed, embeddable videos still belonging to this channel pass normalization; current live or upcoming broadcasts are excluded. It re-sorts real `statistics.viewCount` values and returns up to 12. Missing or unsafe counts remain `null`, never invented. The label states that these are most-viewed public embeddable uploads in at most 100 API search results. YouTube's channel-filtered public search is itself capped at 500 videos and can have index omissions; this is not guaranteed to exhaust every channel upload. API embedding eligibility does not guarantee availability in every viewer's region or account. [9] [10]

Twitch clip `embedUrl` is a canonical base URL; the frontend must append `parent=window.location.hostname` and any ancestor embed domains. Twitch requires parent parameters and HTTPS. Do not derive an embed parent from an untrusted request header in the backend. YouTube embeds use `https://www.youtube-nocookie.com/embed/{id}`. Use normal links as a fallback when embedding is unavailable. Spotify artwork and metadata must retain links back to Spotify, be attributed with the Spotify logo, and must not be cropped or altered. [11] [7]

## Caching, errors, and checks

Caches are bounded, in-memory, and shared by all visitors within one process. Concurrent reads coalesce into one load per fixed cache key. Music responses cache for 20 seconds, library samples for 60 seconds, and clips for 15 minutes. Errors and disconnected responses cache for 15 seconds. Tokens refresh 60 seconds before expiration. Twitch app tokens are validated on acquisition and at least hourly when reused by active requests; no user OAuth session is maintained. Credential changes invalidate all caches. Every upstream request has an eight-second timeout and refuses redirects; Spotify library data requests also share a thirty-second refresh budget. Requests never follow provider-supplied pagination URLs, only their bounded offsets/cursors. HTTP 401 causes at most one token renewal/retry. HTTP 429 creates a provider-wide cooldown respecting `Retry-After`, capped at one hour; other failures are sanitized without returning or logging raw upstream bodies, URLs containing keys, or secrets. No stale-on-error library fallback is used. [12]

Run `pnpm exec vitest run server/integrations.test.ts` for integration tests and `pnpm check` for TypeScript. Tests use injected fetch/environment/clock values; they do not call real provider APIs, perform OAuth, or require credentials.
